# 涅凰智农 IoT 当前产品现状与 Gap

> 更新日期：2026-07-05  
> 口径：本文件记录当前代码真实实现和硬件端最新逻辑带来的产品/联调差距，不以历史方案文档中的设想为准。

## 一、当前结论

当前系统已经从“只靠 HTTP Adapter 上报 JSON”的阶段，推进到：

```text
硬件网关 TCP
  -> Go gateway-adapter 原始收包和 raw journal
  -> 全量 raw frame 上报 Go 服务
  -> Go 服务先写 raw_device_events，再最小解析 register/heartbeat
  -> Go nehuang-server 维护 MySQL 主模型
  -> Admin 按设备网关管理设备和绑定
  -> Mini/C 端查看已绑定设备并创建异步控制命令
```

当前最关键的边界是：

- `gateway-adapter` 先解决“真实硬件 bytes 能稳定进云端、能留痕、能回放”。
- `nehuang-server` 继续作为业务事实来源，负责用户、绑定、设备点位、控制命令、Admin/Mini API。
- 硬件端最新文档中的累计工作包、告警重复上报、ACK/清缓存语义还没有完成代码实现。
- 硬件端 2026-07-05 晚新增 TDMA 口径：200 秒时隙表盘由云边硬件侧新增 MCU 维护，云端不再按公网延迟卡窗口；云端新增职责是上下行包 6 字节时分秒字段的生成、解析和入库时间反填。
- 硬件端最新沟通补充了注册/绑定产品口径：设备网关先通过合法心跳入库，并携带 `access_mode`（`shared`/`exclusive`）；采集执行器挂在设备网关下，并可由管理员或农户端用频点和 ID 绑定到具体农户。
- `access_mode` 口径：
  - `exclusive`：默认该网关绑定可按网关展开全部采集执行器（兼容早期单用户场景）。
  - `shared`：共享网关不能默认展开全部采集执行器，农户端/绑定列表按“采集执行器-功能点授权”展示。
- 硬件协议字段未最终冻结前，采集执行器不做自动同步；采集执行器建档先由管理端/农户在网关上下文手工建立。

因此，当前产品已经具备 **本地/云端联调入口**，但还不是完整硬件闭环。

### 2.2 Gateway Adapter

已实现：

- 独立二进制 `cmd/gateway-adapter`。
- TCP 监听硬件网关连接，默认 `NEHUANG_GATEWAY_TCP_ADDR=:8081`。
- 健康检查端口，默认 `NEHUANG_GATEWAY_HEALTH_ADDR=:18081`。
- 每个 TCP 连接生成 `connection_id`。
- 收到任何 bytes 后立即写 raw frame journal。
- 将每次 TCP read 到的原始 bytes 上报到 `POST /api/v1/adapter/raw-frames`。
- runtime log 使用结构化 JSON。
- debug/protocol log 通过 `NEHUANG_GATEWAY_DEBUG=true` 开启。
- 识别 ASCII `FP_xxx` 注册包。
- 识别 `keepalive/keepalive message/HEARTBEAT/HB/PING/HEART` 心跳包。
- 注册/心跳的业务解析由 Go 服务在 raw frame 落库后完成。
- CRC-16/MODBUS 固定实现。
- `cmd/gateway-adapter-mock` 可模拟注册、keepalive 心跳、Modbus 读指令、工作包、告警包、未知包。
- `cmd/gateway-adapter-mock` 当前支持一次性发送注册、keepalive 心跳、Modbus 读指令、工作包、告警包、未知包，并可通过 `-repeat/-delay` 做短时重复发送。
- 为联调，`gateway-adapter-mock` 可通过重复发送实现持续 keepalive 测试；长周期 loop 化脚本仍属于下一轮工具优化。
- `cmd/gateway-adapter-mock` 可进入等待下行模式，打印 Adapter 写回 TCP 的 command hex。
- “注册一次后长期 keepalive、定期发送模拟包”的 loop 模式属于下一轮工具增强（当前通过 `-repeat/-delay` 组合临时模拟）。
- `cmd/gateway-adapter-replay` 可回放 raw journal 并统计分类结果。
- 识别出设备网关后，Adapter 会按 `gateway_external_id` 拉取 pending command。
- Adapter 能把 pending command 的 `command_hex` 写回当前 TCP 连接，并在成功写回后标记 `sent`。

当前限制：

- 工作包已经能进入 Go 服务 `raw_device_events`，但仍不解析字段。
- 告警包已经能进入 Go 服务 `raw_device_events`，但仍不入业务告警。
- 下行 hex 写回已经具备 Mock 演示能力；真实硬件 ACK 语义仍待确认。
- 未实现 2026-07-05 TDMA 口径下行 6 字节时分秒生成、上行 6 字节时分秒解析与业务数据时间反填（仅保留口径定义，暂不入业务）。

### 2.4 设备接入与主数据

当前设备主数据仍以硬件上报为主，但采集执行器部分需要手工建档补齐：

- raw frame 中的 register/heartbeat 会创建或更新 `cloud_gateways`。
- telemetry/work 后续应创建或更新：
  - `collector_nodes`
  - `device_points`
  - `sensor_data`
  - `device_realtime_maps`

当前未实现“后台手动新增网关”作为正式建档流程；`collector_nodes` 在协议未冻结前不做硬件自动同步，当前采用网关上下文中的手工建档作为正式入口。

已补充联调辅助能力：

- 在设备网关已注册后，Admin 设备管理可对选中的设备网关执行“添加采集执行器”。
- 该入口会创建或更新一个 `collector_nodes` 采集执行器和默认 4 个 `device_points`：温度、墒情、水泵、风机。
- 该入口用于在协议未冻结阶段先建立云端采集执行器档案，不代表真实硬件工作包字段已经冻结。

历史实现中的后台默认绑定口径是：

```text
农户
  -> 设备网关
  -> 设备网关下所有采集执行器和功能点
```

该口径只适合设备网关由单个农户独占的场景（`exclusive`）。最新产品口径中，网关可以作为共享接入设施服务多个农户，`shared` 场景下不能因为绑定网关就默认展开该网关下全部采集执行器。

后续更准确的默认授权口径应调整为：

```text
设备网关
  -> 采集执行器
    -> 功能点

农户
  -> 采集执行器 / 功能点授权
```

设备网关与农户之间需要区分：

- 安装/资产归属：设备网关安装在某个农户处，资产和维护可能归该农户。
- 接入共享：附近其他农户可以共享该设备网关。
- 数据/控制权限：农户只能看到和控制绑定给自己的采集执行器和功能点。

旧版“绑定功能点”继续保留兼容：

```text
从已经上报并入库的 device_points 中选择一个功能点
  -> 绑定给某个农户
```

不是：

```text
管理员手动填写 gateway / frequency / device_external_id / function_type
  -> 创建一个新硬件设备
```

但最新沟通显示，采集执行器的实际绑定可能就是在已选设备网关下填写“频点 + 采集执行器 ID”。云端仍需要明确：

- 采集执行器是否会由设备网关主动上报注册信息。
- 如果不上报，管理员/农户端手动填写“设备网关 + 频点 + ID”是否就视为创建采集执行器。
- 如何校验该频点和 ID 真实存在，避免绑定到错误网关或错误采集执行器。

## 三、硬件端最新文档带来的新增要求

硬件端最新逻辑说明书明确了以下方向：

- MCU 本地承担温控判断和保护逻辑，云端不再执行旧 `jisuan.py`。
- MCU 每 5 分钟缓存一组温度；历史方案是 4 小时上报 48 组，最新预期因新增时间字段改为约 2 小时一次上报。
- 最新沟通又补充了“云端点名/读取”的工作口径：云端可以点名采集执行器读取实时温度和 I/O 状态；也可以每 4 小时读取一次累计温度记录。该口径与此前“标准工作包硬件主动上报”的理解存在差异，需要最终协议文档统一。
- 旧标准工作包最大约 163 字节；新增 6 字节时间字段后的最大长度待重新计算。
- 云端读取成功后，需要通知 MCU 清空缓存并重新计时。
- 单个云边集群按最多 100 台采集执行器规划，每台 2 秒专有时序，满配 200 秒周期。
- 上摆周期用于云端下发读取/控制/同步；下摆周期用于 MCU 上报。
- 200 秒时隙表盘、上摆/下摆时序由硬件侧新增 MCU 维护；云端只在下行包内携带北京时间时分秒标记。
- 下行包在包头地址信息后、正式内容前新增 6 字节时分秒；上行包在地址/频点 ID 后、正式内容前新增 6 字节时分秒。
- 告警包需要在后续 3 个自有时隙重复上报，云端需要去重。
- 手动控制命令暂定为 `F0` 开、`0F` 关、`00` 停。
- Modbus CRC-16 作为包级校验，云端和硬件端算法必须一致。

这些要求已经整理到 `docs/hardware_protocol_current.md`。

## 五、已知信息到实现概况

### 5.1 已知信息

| 已知信息 | 对云端的含义 | 当前实现概况 |

| 采集执行器可由管理员或农户端绑定 | 采集执行器建档应由管理端在网关上下文手工提交；协议冻结前不依赖工作包自动同步 | 当前已支持管理端在网关下手工建档采集执行器，并支持 `binding_type=collector` |
| 云端可以点名读取/下发控制 | 下行命令需要目标设备网关、频点、采集执行器 ID、命令 Hex | 当前已支持自定义 `command_hex`、pending/sent 链路和 Adapter TCP 写回 |
| 温度/告警/ACK 字段未冻结 | 真实 parser 不能写死字段偏移 | 当前 raw 留痕和回放链路已具备，工作包/告警包仍待解析 |
| 200 秒窗口由硬件侧维护 | 云端不应按公网延迟卡 2 秒窗口 | 当前控制链路是异步 pending 模型，方向正确；仍需确认硬件侧缓存/失败规则 |

### 5.2 已明确且可先实现的部分

这些任务不依赖真实工作包字段，不需要等待温度编码、ACK、清缓存和 CRC 覆盖范围确认。

| 优先级 | 可实现项 | 需要做什么 | 验收口径 |
|--------|----------|------------|----------|
| 已完成 | 共享设备网关绑定模型 | 取消“一台设备网关只能有一个 active 农户绑定”的限制；候选列表不再只返回未绑定网关；绑定列表展示共享状态 | 同一个共享设备网关可绑定给多个农户；独享设备网关仍防止跨农户重复绑定 |
| 已完成 | C 端按采集执行器/功能点授权展示 | 农户端不再因绑定共享设备网关而自动看到该网关下所有功能点；默认展示绑定给自己的采集执行器/功能点 | A 农户和 B 农户共享同一设备网关时，只看到各自绑定的采集执行器/功能点 |
| 已完成 | 采集执行器正式建档入口 | 在设备网关详情中新增正式“添加采集执行器”入口，输入频点、采集执行器 ID、名称、棚号、备注；可创建默认功能点 | 管理员能在已注册设备网关下创建采集执行器；设备树和绑定候选能看到 |
| 已完成 | 采集执行器绑定农户 | 新增 `binding_type=collector`，支持 `农户 -> 采集执行器`；兼容旧 `农户 -> 功能点` | 农户绑定采集执行器后，C 端展示该采集执行器下功能点；解绑后不可见 |
| 已完成 | 农户端设备列表分组 | 农户端按采集执行器分组展示功能点，设备网关只作为“接入网关”信息 | 列表从“功能点平铺”调整为“采集执行器分组 + 功能点” |
| 已完成 | 管理端共享网关提示 | 设备网关详情、绑定管理、农户详情展示共享/独享模式和采集执行器绑定 | 后台能解释为什么同一设备网关出现在多个农户名下 |
| 已完成 | 操作日志复核和补测试 | 绑定、解绑、添加采集执行器、修改网关模式写入 `op_records` | 操作日志可看到绑定、解绑、配置类操作 |
| P1 | 下行目标说明增强 | 控制日志和下行弹窗展示设备网关、频点、采集执行器 ID、功能点、command_hex | 硬件端看到下行 Hex 时，后台能对应到目标采集执行器 |

### 5.3 不能先实现或只能做骨架的部分

这些任务还缺少真实协议样例，不能写死生产逻辑。

| 暂缓项 | 暂缓原因 | 当前可做的替代动作 |
|--------|----------|------------------|
| 工作包 parser | 温度字段、长度、时间字段、CRC 覆盖范围未冻结 | 继续 raw 入库、payload 摘要、replay 工具 |
| 告警 parser 和去重 | 告警字段和恢复口径未冻结 | 继续显示为告警/未知包，保留 raw |
| ACK 成功/失败判定 | ACK bytes 语义未确认 | 控制命令只做到 pending/sent/timeout |
| 清缓存命令 | 清缓存 Hex 和触发条件未确认 | 后台保留自定义 Hex 下发，不做固定按钮 |
| 4 小时读取调度 | “云端点名读取”还是“硬件主动上报”仍有冲突 | 先做手动读取 Hex，下阶段再定时任务化 |
| 6 字节时间字段 | 编码、位置、是否参与 CRC 未确认 | 文档保留字段，代码暂不写死 |

### 5.4 建议下一轮实现顺序

1. 等真实 raw 样例稳定后，再做 parser：
   - 工作包 parser。
   - 告警 parser/去重。
   - ACK parser。
2. 明确四小时缓存读取/清缓存策略：
   - 云端定时点名还是硬件主动上报。
   - 清缓存是否按滚动窗口清理。
3. 继续增强农户端自助绑定：
   - 农户选择设备网关后输入频点 + 采集执行器 ID。
   - 后端校验规则等待硬件端确认。
   - ACK/清缓存。
   - 周期读取调度。

## 六、当前最优先确认事项

1. 真实硬件 TCP 到云端 Adapter 的联调方式：
   - 硬件网关是否可以作为 TCP client 连接云端 `IP:8081`。
   - 注册包和心跳包真实 bytes 是什么。
   - 工作包真实 bytes 样例是什么。
2. 工作包字段：
   - `AA AA` 是 2 字节设备 ID 还是两个独立字段。
   - 温度 `XX XX` 是否为有符号 16 位，是否除以 10。
   - 6 字节时分秒字段的编码方式、时区、插入位置和是否参与 CRC。
   - `YY` 是总长度还是数据组数。
   - CRC 覆盖范围和字节顺序。
3. 时隙/控制：
   - 硬件侧新增 MCU 如何缓存和转发云端 pending command。
   - 网络延迟导致命令错过窗口时，硬件侧丢弃、重试还是回失败。
   - MCU 是否支持主动取 pending command。
4. ACK/清缓存：
   - MCU 上报历史数据后，云端用什么包确认收到。
   - MCU 什么时候清空缓存。
   - 连续失败 5 次后的告警和数据丢弃如何对用户展示。
5. 产品流程：
   - 采集执行器是否必须由设备网关真实上报后才出现在后台。
   - 是否允许管理员/农户端在已选设备网关下填写频点和 ID，直接创建采集执行器档案。
   - 农户端是否只展示绑定给自己的采集执行器/功能点。
   - 新设备首次上报后是否进入“待配置/待确认”列表。
   - 设备网关共享给多个农户时，资产归属、维护权限、查看权限、控制权限如何区分。

## 七、建议下一步

当前下一步不应先做复杂 UI，而应先完成硬件接入的最小闭环：

1. 把本轮 Admin/Adapter 改动部署到腾讯云。
2. 用 `gateway-adapter-mock -wait-downlink` 验证控制命令从 Server 到 TCP 下行。
3. 让硬件网关连 TCP 端口并发送注册、心跳、工作包样例。
4. 用 raw journal 和 replay 工具确认真实包形态。
5. 根据真实样例补 parser。
6. 先打通：
   - 注册
   - 心跳
   - 一个工作包入 `sensor_data`
   - 一个告警包入告警记录
   - 一个控制命令 pending -> sent -> ack
6. 再补 Admin/Mini 的完整展示和操作体验。

在真实 raw 包稳定前，不建议把字段偏移、时隙策略、ACK/清缓存语义写死进生产业务逻辑。
