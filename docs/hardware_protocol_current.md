# 涅凰智农硬件协议当前摘要

> 更新日期：2026-07-05  
> 来源：硬件端最新《涅凰智农小程序硬件侧逻辑说明书》，以及当前已达成的云端/硬件边界共识。
> 口径：本文只整理与云端实现、联调和产品验收有关的内容。MCU 内部控制算法、端口接线和本地硬件实现细节只作为背景，不作为云端业务逻辑。

联调口径更新（2026-07-05）：

- 下行优先采用自定义 hex，不在联调期提前约束标准下行语义。
- 最新沟通中，工作数据被拆成三类：云端点名读取实时数据、云端下发控制/阈值类工作数据、云端周期读取累计温度记录。
- 累计温度记录当前按“云端每 4 小时读取一次，硬件返回前 4 小时每 5 分钟一组记录”理解；此前“MCU 主动上报标准工作包”的口径需要用最终协议样例统一。
- 临时读取场景按“云端下发读取 hex -> MCU 返回 raw 工作包”执行。
- 真实 ACK、清缓存命令语义、工作包字段含义仍待确认，当前以 raw 落盘与状态链路为准。

硬件端 TDMA 时间同步口径更新（2026-07-05 晚）：

- 200 秒时隙表盘、上摆/下摆时序不再由云端卡窗口执行，改由云边硬件侧新增 MCU 维护。
- 云端需要在每个下行指令包的“包头地址信息之后、正式内容之前”增加 6 字节时分秒标记，用于硬件侧做 TDMA 时间同步。
- 硬件上行包也会在“地址/频点 ID 信息之后、正式内容之前”增加 6 字节时分秒标记；序号字段仍保留。
- 云端后续 parser 需要读取该 6 字节时分秒，并把对应设备数据按该时间点反填/倒排入库。
- 由于时间字段增加后 MCU 缓存压力上升，硬件端预期将标准累计上报周期由 4 小时调整为 2 小时。
- 6 字节时间字段的编码方式、时区、插入偏移、是否参与 CRC，仍待硬件端最终文档和样例包确认。

## 1. 云端需要关心的边界

当前按四层理解：

```text
采集执行器 MCU
  -> 云边/LoRa/TCP 硬件网关
  -> Go gateway-adapter
  -> Go nehuang-server + MySQL + Admin/Mini
```

职责划分：

- 采集执行器 MCU：负责本地温控判断、继电器保护、5 分钟温度记录缓存、限位/故障状态采集。
- 云边/LoRa/TCP 硬件网关：负责把 MCU 上行 bytes 透传到云端 TCP Adapter，并把云端下行 bytes 透传给目标 MCU。
- Go `gateway-adapter`：负责 TCP 接入、连接状态、原始 bytes 第一时间落盘、最小报文分类、向 Go 服务转发已确认事件。
- Go `nehuang-server`：负责用户、绑定、点位配置、控制命令状态机、MySQL 固化、Admin/Mini API。

云端不负责：

- 重写 MCU 自动温控算法。
- 直接读取 NTC 温度模块。
- 直接控制每个硬件端口。
- 解决同频空中撞包本身。

云端必须负责：

- 稳定接收硬件网关发来的原始 bytes。
- 保留 raw journal 便于协议变化后回放。
- 按最终协议解析工作包、告警包、ACK。
- 记录控制命令的 pending/sent/ack/succeeded/failed/timeout 状态。
- 给 Admin/Mini 展示设备、曲线、告警和控制结果。

## 1.1 最新注册和绑定口径

最新沟通补充了设备注册和绑定的产品过程：

```text
设备网关合法心跳
  -> 云端识别并入库设备网关
  -> 管理员把设备网关绑定给农户或标记安装/资产归属
  -> 采集执行器挂在该设备网关下
  -> 管理员或农户端用频点和采集执行器 ID 绑定采集执行器
  -> 农户端展示绑定给该农户的采集执行器和功能点
```

关键变化：

- 设备网关可以被多个农户共享使用，不一定只归一个农户独占使用。
- 采集执行器不能直接联网，云端要点名采集执行器时，必须先定位设备网关，再用频点和采集执行器 ID 定位目标。
- 仅有“频点 + ID”不足以在云端全局定位采集执行器，必须有设备网关上下文。
- 农户端不应默认展示共享设备网关下所有采集执行器；应只展示绑定给该农户的采集执行器和功能点。

仍未明确：

- 采集执行器是否会由设备网关主动上报注册。
- 如果不上报，管理员/农户端填写“设备网关 + 频点 + ID”是否就视为建档。
- 云端如何校验手动填写的频点和 ID 对应真实存在的采集执行器。

## 2. 当前报文分类

| 报文 | 方向 | 当前理解 | 当前实现状态 |
|------|------|----------|--------------|
| 注册报文 | 云边网关 -> Adapter -> Server | 云边设备首次上线后上报自定义名称，如 `FP_xxx` | Adapter 已识别 ASCII `FP_xxx` 并转发 register |
| 心跳报文 | 云边网关 -> Adapter -> Server | 云边设备每 30 秒发送极短固定数据，用于判断网关在线 | Adapter 已识别 `keepalive/keepalive message/HEARTBEAT/HB/PING/HEART`；server 有离线 scanner |
| 时间同步/握手报文 | Server/Adapter -> 云边网关 -> MCU；MCU -> 云端 ACK | 下行地址信息后增加 6 字节时分秒，硬件侧据此同步 TDMA 时间；ACK 与触发含义待确认 | 未完整实现；当前只有命令队列骨架 |
| 工作报文 | MCU -> 云边网关 -> Adapter -> Server | 实时读取回复、周期累计温度记录回复、临时读取返回包，均先按 raw 保存；上行地址/频点 ID 后预期增加 6 字节时分秒 | 未解析；当前只落 raw |
| 紧急告警报文 | MCU -> 云边网关 -> Adapter -> Server | R/S 故障时在后续 3 个自有时隙重复上报 | 未解析、未去重；当前只落 raw |
| 控制指令 | Admin/Mini -> Server -> Adapter -> 云边网关 -> MCU | 手动开/关/停、切换自动/手动、读取缓存 | Server 已创建异步命令；Adapter 下发和 ACK 解析未完成 |
| 清缓存/确认指令 | Server/Adapter -> 云边网关 -> MCU | 云端确认收到历史数据后，通知 MCU 清空缓存并重新计时 | 语义待硬件端最终确认，未实现 |

## 3. 工作数据包当前格式

硬件端文档给出的累计工作包格式：

```text
AA AA BB CC XX XX DD XX XX EE XX XX FF XX XX GG XX XX ... R S T U V W YY ZZ
```

最新预期会在地址/频点 ID 后、正式数据前增加 6 字节时分秒字段：

```text
AA AA BB TT TT TT TT TT TT CC XX XX DD XX XX ... R S T U V W YY ZZ
```

> 注：`TT...` 只是文档占位，不代表最终编码。最终需以硬件端样例包确认 6 字节是 BCD、ASCII、二进制整数，还是其他格式。

字段当前理解：

| 字段 | 含义 |
|------|------|
| `AA AA` | 采集执行器 ID |
| `BB` | 采集执行器频点 |
| `TT...` | 6 字节时分秒时间标记；用于云端按硬件实际时点反填/倒排数据，编码待确认 |
| `CC/DD/EE/...` | 每 5 分钟一组温度记录的序号 |
| `XX XX` | 对应序号下的温度数值 |
| `R` | DI3，卷帘轨道故障告警；`0x00` 正常，`0xFF` 脱轨 |
| `S` | DI4，卷帘机过卷/过放告警；`0x00` 正常，`0xFF` 告警 |
| `T` | 继电器 1 状态；`0x00` 开启，`0xFF` 关闭 |
| `U` | 继电器 2 状态；`0x00` 开启，`0xFF` 关闭 |
| `V` | DI1，上限位；`0x00` 开路，`0xFF` 短路 |
| `W` | DI2，下限位；`0x00` 开路，`0xFF` 短路 |
| `YY` | 数组总长度 |
| `ZZ` | Modbus CRC-16，2 字节 |

周期和触发口径：

- MCU 每 5 分钟存储一组温度。
- 历史理解是 4 小时累计 48 组后集中上报。
- 最新沟通口径是云端每 4 小时点名读取一次当前采集执行器前 4 小时累计温度记录，每 5 分钟一组。
- 是否保留硬件主动周期上报，或改成纯云端点名读取，需要最终协议样例确认。
- 此前还出现过“因增加 6 字节时间字段导致 MCU 缓存压力上升，改为约 2 小时一次累计上报”的口径；该周期与 4 小时读取口径需要统一。
- MCU 缓存最多约 50 组温度记录。
- 旧标准完整报文最大约 163 字节；新增时间字段后的最大长度待重新计算。
- 如果 Admin/Mini 临时读取，返回自上次读取以来的累计记录 raw，长度可能小于 163 字节。

### 3.1 联调期间临时读取与周期读取

- 最新口径下，云端可以通过 `command_hex` 点名采集执行器读取实时数据或累计记录。
- 临时读取按 `command_hex` 下发读取口径处理，返回的是 raw 工作包；收到 raw 后做回放留存，等字段协议确认后再落解析。
- 周期累计温度记录是“硬件主动上报”还是“云端 4 小时点名读取”，当前仍需最终确认。

云端处理原则：

- 当前真实工作包未冻结前，Adapter 只写 raw journal，不写死字段偏移。
- 后续 parser 必须先校验包头、长度、CRC，再解析温度序列和 I/O 状态。
- 解析成功后写 `sensor_data`，同步 `device_points` 和 `device_realtime_maps`。
- 解析失败保留 raw，支持 replay 工具回放。

## 4. 告警包当前格式

硬件端文档给出的紧急告警包：

```text
AA AA BB FF FF FF ZZ
```

变体：

```text
AA AA BB FF FF 00 ZZ  # R 告警
AA AA BB FF 00 FF ZZ  # S 告警
```

当前理解：

- 第一个 `FF` 是告警警示字段。
- 第二个字段表示 R 告警。
- 第三个字段表示 S 告警。
- R 或 S 出现 `0xFF` 后，MCU 在后续 3 个自有下摆时隙重复上报同一告警。
- 云端需要按设备、告警类型、原始包 hash、时间窗口去重，避免 3 次重复上报产生 3 条用户通知。

当前实现状态：

- Adapter 可以把 alarm-looking frame 分类为 `alarm`，但不会入告警业务表。
- 告警解析、去重、通知推送均未实现。

## 5. 时隙和周期当前理解

硬件端当前设计：

- 单个云边集群按最多 100 台采集执行器规划。
- 每台采集执行器分配 2 秒专有时序周期。
- 满配 100 台时，一个完整轮询周期为 200 秒。
- 每台设备的 2 秒周期分为上摆周期和下摆周期。
- 上摆周期：设备不发上行数据，等待云端下发读取/控制/同步指令。
- 下摆周期：云端不下发，等待该设备上报数据。
- 上摆/下摆前后各有 100ms 缓冲保护时序，避免空中数据和总线数据撞包。
- 最新口径：云边硬件侧会新增 MCU 维护 TDMA 表盘、上摆/下摆时序和同步逻辑；云端不再负责按公网时间精确卡 2 秒窗口。
- 云端只需在下行包中携带当前北京时间的 6 字节时分秒标记，硬件侧据此完成时间同步。
- 上行包中同样携带 6 字节时分秒，云端按该时点反填业务数据时间。

云端风险判断：

- 如果由云端直接卡毫秒级窗口主动下发，公网延迟、进程调度、TCP 抖动都会显著增加工程风险。
- 最新硬件方案已经把时隙维护放到靠近硬件的一侧，云端不做 200 秒表盘调度。
- 云端仍按异步控制命令模型创建 pending command，由 Adapter/硬件侧在可下发窗口内处理并回写 ACK。
- 当前代码选择异步控制命令模型：用户请求不长时间阻塞等待 MCU，而是返回 `command_id + pending`。

待确认：

1. 下行 6 字节时分秒字段的编码方式、时区和字节顺序。
2. 上行 6 字节时分秒字段的插入位置、编码方式和是否参与 CRC。
3. `AA AA BB XX YY` 在读取、阈值同步、时序起点中的具体语义待确认。
4. `AA AA BB ZZ` 在 ACK、清缓存确认、执行完成间是否复用待确认。
5. 网络延迟导致错过窗口时，硬件侧缓存、丢弃或重试规则仍待确认。

## 6. 控制指令当前理解

硬件端文档中的手动控制指令：

| 指令 | 当前理解 |
|------|----------|
| `AA AA BB F0` | 远程开启 |
| `AA AA BB 0F` | 远程关闭 |
| `AA AA BB 00` | 远程停止 |
| `AA AA BB XX YY` 且 `XX == YY` | MCU 认定进入手动状态 |
| `AA AA BB XX YY` 且正常上下阈值 | MCU 回到自动温控（待确认） |

安全逻辑：

- 开启/关闭指令在 MCU 内固定 15 秒保护时间。
- 15 秒内无操作后回归停止。
- R/S 故障时自动控制和手动控制都停止，MCU 不输出。
- 上下限位触发时，对应方向禁止输出。

当前服务端实现：

- Mini 控制请求会创建 `control_commands`，立即返回 pending。
- Adapter 内部接口支持拉取 pending、标记 sent、回写 result。
- 尚未实现正式时间同步字段生成、真实 hex 下发、ACK 解析和最终 succeeded/failed 判定。

## 7. CRC 当前口径

当前使用 Modbus CRC-16：

- 初始值：`0xFFFF`
- 多项式：`0xA001`
- 输出：低字节在前，高字节在后

云端已经有固定实现：

- `internal/gatewayadapter/protocol/crc.go`
- 标准样例 `123456789 -> 0x4B37`

需要确认的不是算法本身，而是：

1. CRC 覆盖哪一段 bytes。
2. 包尾 `ZZ` 的两个字节顺序。
3. `YY` 长度字段是否参与 CRC。
4. 告警包、ACK 包、控制结果包是否全部带 CRC。

## 8. 当前未实现清单

- 真实工作包 parser。
- 紧急告警 parser。
- 告警去重和通知。
- 云端不再实现 200 秒时隙调度；需实现时间同步字段生成/解析。
- 上下行 6 字节时间字段生成、解析和入库反填。
- 约 2 小时累计记录的字段解析冻结与校验策略确认。
- 读取成功后清 MCU 缓存命令语义确认。
- 控制命令真实下发与回执链路。
- ACK/执行结果解析。
- 断线重连后的命令恢复策略。
- 与真实硬件的端到端联调。

这些能力不应在协议样例未冻结前写死到生产逻辑中。
