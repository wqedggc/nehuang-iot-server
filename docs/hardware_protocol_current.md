# 涅凰智农硬件协议当前摘要

> 更新日期：2026-07-05  
> 来源：甲方最新《涅凰智农小程序硬件侧逻辑说明书》，以及当前已达成的云端/硬件边界共识。  
> 口径：本文只整理与云端实现、联调和产品验收有关的内容。MCU 内部控制算法、端口接线和本地硬件实现细节只作为背景，不作为云端业务逻辑。

## 1. 云端需要关心的边界

当前按四层理解：

```text
采集执行器 MCU
  -> 云边/LoRa/TCP 硬件网关
  -> Go gateway-adapter
  -> Go nehuang-server + MySQL + Admin/Mini
```

职责划分：

- 采集执行器 MCU：负责本地温控判断、继电器保护、5 分钟温度记录缓存、限位/故障状态采集。
- 云边/LoRa/TCP 硬件网关：负责把 MCU 上行 bytes 透传到云端 TCP Adapter，并把云端下行 bytes 透传给目标 MCU。
- Go `gateway-adapter`：负责 TCP 接入、连接状态、原始 bytes 第一时间落盘、最小报文分类、向 Go 服务转发已确认事件。
- Go `nehuang-server`：负责用户、绑定、点位配置、控制命令状态机、MySQL 固化、Admin/Mini API。

云端不负责：

- 重写 MCU 自动温控算法。
- 直接读取 NTC 温度模块。
- 直接控制每个硬件端口。
- 解决同频空中撞包本身。

云端必须负责：

- 稳定接收硬件网关发来的原始 bytes。
- 保留 raw journal 便于协议变化后回放。
- 按最终协议解析工作包、告警包、ACK。
- 记录控制命令的 pending/sent/ack/succeeded/failed/timeout 状态。
- 给 Admin/Mini 展示设备、曲线、告警和控制结果。

## 2. 当前报文分类

| 报文 | 方向 | 当前理解 | 当前实现状态 |
|------|------|----------|--------------|
| 注册报文 | 云边网关 -> Adapter -> Server | 云边设备首次上线后上报自定义名称，如 `FP_xxx` | Adapter 已识别 ASCII `FP_xxx` 并转发 register |
| 心跳报文 | 云边网关 -> Adapter -> Server | 云边设备每 30 秒发送极短固定数据，用于判断网关在线 | Adapter 已识别 `HEARTBEAT/HB/PING/HEART`；server 有离线 scanner |
| 时序/握手报文 | Server/Adapter -> 云边网关 -> MCU；MCU -> 云端 ACK | 云端下发 `AA AA BB XX YY`，MCU 以 `AA AA BB ZZ` 确认并开始/校正时序 | 未完整实现；当前只有命令队列骨架 |
| 工作报文 | MCU -> 云边网关 -> Adapter -> Server | MCU 上报 4 小时累计温度记录和 I/O 状态 | 未解析；当前只落 raw |
| 紧急告警报文 | MCU -> 云边网关 -> Adapter -> Server | R/S 故障时在后续 3 个自有时隙重复上报 | 未解析、未去重；当前只落 raw |
| 控制指令 | Admin/Mini -> Server -> Adapter -> 云边网关 -> MCU | 手动开/关/停、切换自动/手动、读取缓存 | Server 已创建异步命令；Adapter 下发和 ACK 解析未完成 |
| 清缓存/确认指令 | Server/Adapter -> 云边网关 -> MCU | 云端确认收到历史数据后，通知 MCU 清空缓存并重新计时 | 语义待甲方最终确认，未实现 |

## 3. 工作数据包当前格式

甲方文档给出的累计工作包格式：

```text
AA AA BB CC XX XX DD XX XX EE XX XX FF XX XX GG XX XX ... R S T U V W YY ZZ
```

字段当前理解：

| 字段 | 含义 |
|------|------|
| `AA AA` | 采集执行器 ID |
| `BB` | 采集执行器频点 |
| `CC/DD/EE/...` | 每 5 分钟一组温度记录的序号 |
| `XX XX` | 对应序号下的温度数值 |
| `R` | DI3，卷帘轨道故障告警；`0x00` 正常，`0xFF` 脱轨 |
| `S` | DI4，卷帘机过卷/过放告警；`0x00` 正常，`0xFF` 告警 |
| `T` | 继电器 1 状态；`0x00` 开启，`0xFF` 关闭 |
| `U` | 继电器 2 状态；`0x00` 开启，`0xFF` 关闭 |
| `V` | DI1，上限位；`0x00` 开路，`0xFF` 短路 |
| `W` | DI2，下限位；`0x00` 开路，`0xFF` 短路 |
| `YY` | 数组总长度 |
| `ZZ` | Modbus CRC-16，2 字节 |

周期：

- MCU 每 5 分钟存储一组温度。
- 标准 4 小时累计 48 组后集中上报。
- MCU 缓存最多约 50 组温度记录。
- 标准完整报文最大约 163 字节。
- 如果 Admin/Mini 临时读取，返回自上次读取以来的累计记录，长度可能小于 163 字节。

云端处理原则：

- 当前真实工作包未冻结前，Adapter 只写 raw journal，不写死字段偏移。
- 后续 parser 必须先校验包头、长度、CRC，再解析温度序列和 I/O 状态。
- 解析成功后写 `sensor_data`，同步 `device_points` 和 `device_realtime_maps`。
- 解析失败保留 raw，支持 replay 工具回放。

## 4. 告警包当前格式

甲方文档给出的紧急告警包：

```text
AA AA BB FF FF FF ZZ
```

变体：

```text
AA AA BB FF FF 00 ZZ  # R 告警
AA AA BB FF 00 FF ZZ  # S 告警
```

当前理解：

- 第一个 `FF` 是告警警示字段。
- 第二个字段表示 R 告警。
- 第三个字段表示 S 告警。
- R 或 S 出现 `0xFF` 后，MCU 在后续 3 个自有下摆时隙重复上报同一告警。
- 云端需要按设备、告警类型、原始包 hash、时间窗口去重，避免 3 次重复上报产生 3 条用户通知。

当前实现状态：

- Adapter 可以把 alarm-looking frame 分类为 `alarm`，但不会入告警业务表。
- 告警解析、去重、通知推送均未实现。

## 5. 时隙和周期当前理解

甲方当前设计：

- 单个云边集群按最多 100 台采集执行器规划。
- 每台采集执行器分配 2 秒专有时序周期。
- 满配 100 台时，一个完整轮询周期为 200 秒。
- 每台设备的 2 秒周期分为上摆周期和下摆周期。
- 上摆周期：设备不发上行数据，等待云端下发读取/控制/同步指令。
- 下摆周期：云端不下发，等待该设备上报数据。
- 上摆/下摆前后各有 100ms 缓冲保护时序，避免空中数据和总线数据撞包。

云端风险判断：

- 如果由云端直接卡毫秒级窗口主动下发，公网延迟、进程调度、TCP 抖动都会显著增加工程风险。
- 更稳妥的方向是让靠近硬件的一侧维护时隙，云端只创建 pending command，Adapter/硬件网关在合适窗口下发并回写 ACK。
- 当前代码选择异步控制命令模型：用户请求不长时间阻塞等待 MCU，而是返回 `command_id + pending`。

待甲方确认：

1. 最终是云端主动按时隙下发，还是 MCU/硬件网关主动取 pending command。
2. `AA AA BB XX YY` 是读取指令、阈值同步指令、握手起点，还是三者合一。
3. `AA AA BB ZZ` 是 ACK、清缓存确认、执行完成确认，还是不同场景复用同一格式。
4. slot index 如何分配，是否由云边硬件网关维护。
5. 网络延迟导致错过窗口时，重试规则由谁负责。

## 6. 控制指令当前理解

甲方文档中的手动控制指令：

| 指令 | 当前理解 |
|------|----------|
| `AA AA BB F0` | 远程开启 |
| `AA AA BB 0F` | 远程关闭 |
| `AA AA BB 00` | 远程停止 |
| `AA AA BB XX YY` 且 `XX == YY` | MCU 认定进入手动状态 |
| `AA AA BB XX YY` 且正常上下阈值 | MCU 回到自动温控 |

安全逻辑：

- 开启/关闭指令在 MCU 内固定 15 秒保护时间。
- 15 秒内无操作后回归停止。
- R/S 故障时自动控制和手动控制都停止，MCU 不输出。
- 上下限位触发时，对应方向禁止输出。

当前服务端实现：

- Mini 控制请求会创建 `control_commands`，立即返回 pending。
- Adapter 内部接口支持拉取 pending、标记 sent、回写 result。
- 尚未实现真实 hex 下发、时隙调度、ACK 解析和最终 succeeded/failed 判定。

## 7. CRC 当前口径

当前使用 Modbus CRC-16：

- 初始值：`0xFFFF`
- 多项式：`0xA001`
- 输出：低字节在前，高字节在后

云端已经有固定实现：

- `internal/gatewayadapter/protocol/crc.go`
- 标准样例 `123456789 -> 0x4B37`

需要甲方确认的不是算法本身，而是：

1. CRC 覆盖哪一段 bytes。
2. 包尾 `ZZ` 的两个字节顺序。
3. `YY` 长度字段是否参与 CRC。
4. 告警包、ACK 包、控制结果包是否全部带 CRC。
